## 环境事实（已确认，不要再假设其他能力）

- 本地：VSCode 编辑，Windows Terminal 里跑本 CLI，shell 以 PowerShell 为主；
  CLI 可读本地文件/项目、可调本地 shell 和其他工具；
  代码只做本地 Git 管理，不必推远程。
- Python 由 uv 管理（版本切换便捷，不必特意关注版本）；
  离线脚本统一用 `uv run` 运行，sqlglot 可从公司内网源安装。
  PowerShell 示例：`uv run --with sqlglot python scripts\extract_lineage.py <目录>`
- Agent 能做的：生成/修改本地 `.sql` 文件；用离线 Python（sqlglot 等）
  做 SQL 解析、血缘提取、格式化。仅限离线可实现的事。
- Agent 不能做的：连接生产 Spark、运行任何 SQL、看数据源。
  本地没有测试/开发环境，不要提议试跑、EXPLAIN、抽样查询。
- 提交审批：公司内部大数据任务调度平台，人工提交，审批对 SQL 无强要求，
  本 Skill 和 Agent 不处理审批环节。脚本中可用 `SET` 参数、
  创建临时表、使用平台封装的自定义 UDF（见 `docs/udf-catalog.md`，
  不在清单内的 UDF 不许自创）。
- 运行反馈：任务跑完后由用户人工进入 SparkUI 复制 YARN/Spark 日志，
  保存成文件放进项目目录，再告诉 Agent 文件路径、由 Agent 直接读文件分析；
  Agent 不自动获取日志。
- MCP：可读部分公司内部公开资料/论坛，但**用 MCP 获取公司 wiki 的 UDF
  文档已实测失败**，不要再提议这条路；UDF 以 `docs/udf-catalog.md`
  手工清单为唯一依据。

## 变量约定（平台只确认过一种形式）

- 设置：`set example='xxx';`　使用：`${example}`
- 这是平台提交过的脚本中唯一用过的形式；平时脚本不太用变量，
  只在确有复用/可配置需求时才引入变量，不要为了炫技把常量全改成变量。
- 其他形式（`$example`、`${hiveconf:xxx}` 等）平台是否支持未验证，
  **暂按不支持处理，禁止生成**——即使 sqlglot 本地能解析也不许用。

## 分区约定（2026-11-06 定版，细节以 `docs/sparksql-style.md` 为准）

- 项目所有脚本只用三个分区名，从未用过 `dt/ds/pt` 等命名；
  遇到其他分区名视为异常，先问，不许当同义词自行替换。
- `pt_d`：天分区，格式 `yyyyMMdd`，含义是该脚本运行周期对应的日期。
  读表必须带 `pt_d` 过滤，写入用 `PARTITION(pt_d=...)`；
  例外（全量快照表等）必须在表卡注明且在方案中说明。
- `pt_h`：小时分区，格式 `HH`（`00`–`23`），是运行周期对应日期的小时
  （如 `00` 分区存 `00:00:00`–`00:59:59` 的数据）。
  小时粒度表在 `pt_d` 之外还必须带 `pt_h` 过滤/写入。
- `device_type`：设备类型分区，固定枚举（如 `Phone`、`Tablet`、`Vision`，
  全量以 `docs/sparksql-style.md` 的全局清单为准，清单外不许自创）。
  需求只涉及单一设备类型时必须带过滤；
  涉及全部设备类型时在方案里明说不加过滤，禁止默认全扫不交代。
- 多级分区排序固定为 `pt_d, pt_h, device_type`（天、小时、设备类型），
  只写实际用到的层级、保持相对顺序。

## 排版约定（只定两条，其余暂不设置）

- 关键字默认小写；以提出需求时的要求为准，当次需求指定其他写法从当次。
- 逗号用字段前逗号（行首逗号）。
- 其余排版/命名/写法细节按 使用者 要求暂不设置、保持现状：
  改老脚本沿用原脚本写法，新脚本不许把任何「建议默认值」当规范套用。
- sqlglot 只用于解析和血缘/分区校验；它的默认 format 输出
  （关键字大写、尾随逗号）与上面两条冲突，禁止拿来当最终排版。

## 脚本注释头（仅正式脚本）

- 正式脚本（长期调度、落表产出）必须带固定注释头，
  模板见 `templates/script-header.md`（真实模板由 使用者 提供后替换，
  在此之前不许自创模板里没有的行）。
- 测试脚本（单次数据分析等一次性脚本）不需要注释头，不要强加。
- 每次修改正式脚本，必须在注释头中新增/更新 `@Modify` 行：
  写明变更日期和改动简述。改了 SQL 没改 `@Modify` 视为未完成。

## 触发场景

写新 SparkSQL、改老脚本需求、把业务需求翻译成 SQL 草稿、
根据项目目录里的运行日志文件定位问题并改 SQL。

## 强制流程（按顺序，不许跳步）

1. **澄清口径**：先确认目标粒度（一行 = 什么）、时间口径（要跑哪个运行周期的 `pt_d`/`pt_h`）、
   涉及的分区范围（天/小时、设备类型范围）、
   指标定义；并确认本次是正式脚本还是测试脚本（决定要不要注释头）。口径不清先问，不猜。
2. **查卡片**：先查本地表卡 / 逻辑卡 / 术语表；UDF 只查 `docs/udf-catalog.md`。
   输入表必须来自表卡或 DDL 等本地已确认来源。
3. **出方案**：先输出简要方案——目标粒度、输入表、分区范围、join 键、去重逻辑——
   等用户确认后再写 SQL。复杂需求不许一口气写完。
4. **写 SQL**：生成本地 `.sql` 文件；按 `docs/sparksql-style.md` 执行，
   其中【已定】项必须遵守、【暂不设置】项保持现状（改老脚本沿用原写法），
   不许自选一种风格全篇套用；变量只用「变量约定」的形式；
   分区按「分区约定」执行；排版按「排版约定」两条执行；
   正式脚本带注释头，改老脚本同步更新 `@Modify`。
5. **离线静态校验（代替试跑）**：在 PowerShell 里用 `uv run` 离线跑——
   sqlglot 按 Spark 方言解析无错误、血缘提取（输入/产出表、join 键、分区过滤）
   与方案一致、排版已按小写关键字 + 前逗号人工核对（不用 sqlglot 默认 format）。
   校验结果随 SQL 一起交付，并明确声明
   「未实际运行，正确性未经执行验证」。
6. **日志闭环（提交后）**：用户人工提交运行后，若失败或结果异常，
   由用户把 SparkUI / YARN 日志保存成文件放进项目目录并给出路径。
   Agent 读文件后先摘录关键报错行和对应 Stage，
   再定位到 SQL 具体位置，给出修改后的完整 `.sql`，
   不要只给口头建议；改正式脚本时同步更新 `@Modify`；
   同一问题反复出现时沉淀到逻辑卡的「坑」一节。

## 红线（违反即停）

- 字段、表必须来自表卡或 DDL；查不到就写「未找到」，不许编造字段名、表名。
- 禁止无分区全表扫描；`INSERT OVERWRITE` 必须带明确分区；
  读表缺 `pt_d`（小时表另缺 `pt_h`）过滤即违规，`device_type` 范围未交代同样违规。
- 禁止 `SELECT *` 落表。
- 变量只许 `set x='...'` + `${x}` 一种形式，其他形式暂按平台不支持，禁止生成。
- 不许声称已验证/已试跑：本地无法运行 SQL，任何交付都要标明只过了静态校验。
- 只出 SQL 草稿，不直连生产执行、不自动上线；提交审批由用户人工完成。
- 样本数据只用脱敏 schema 和聚合统计（分区范围、量级、空值率），不给明细数据；
  凭证不写进 Skill 和知识库。

## 交付自检清单

- [ ] 粒度是否膨胀（join 后行数是否符合目标粒度）
- [ ] join 是否一对多未处理（去重键是否明确）
- [ ] 分区是否裁剪（每个输入表都有 `pt_d` 过滤，小时表另有 `pt_h`，`device_type` 范围已交代）
- [ ] 口径是否与术语表一致
- [ ] 空值 / 枚举值是否按表卡处理
- [ ] UDF 是否都在 `docs/udf-catalog.md` 清单内，`SET`/临时表用法合规
- [ ] 变量是否只有 `set` + `${...}` 一种形式
- [ ] 正式脚本注释头齐全、`@Modify` 已按本次变更更新（测试脚本免）
- [ ] 排版为小写关键字 + 字段前逗号（当次需求另有要求除外）
- [ ] sqlglot 离线解析 + 血缘提取已通过，并已声明未实际运行
