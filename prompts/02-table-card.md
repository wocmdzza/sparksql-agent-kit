# 提示词 2：生成表卡（table-card）

前置：先跑完提示词 1（有 `lineage.json` 和盘点表）。
产出：`docs/table-cards/<表名>.md`，一表一卡。把下面整段复制给内部 Agent：

```text
任务：为 <目标表范围，如：盘点表中出现的所有产出表和输入表>
逐张生成表卡，不要让我从零写。

1. 先读模板 templates/table-card.md 和规范 docs/sparksql-style.md
   （分区格式与 device_type 枚举以规范为准），严格按模板结构输出。
2. 事实来源只有四种，卡片里每项都要能溯源：
   lineage.json、脚本原文、项目内的 DDL 文件（先全局搜索
   CREATE TABLE 语句和 *.ddl/*.sql 建表文件）、docs/udf-catalog.md。
   找不到来源的项标「待人工确认」，不许凭字段名猜业务含义。
3. 各节填法：
   - 分区字段：从各脚本的 PARTITION 子句和分区过滤汇总，
     只写实际出现过的 pt_d/pt_h/device_type 组合，并注明哪些脚本在用。
   - 字段表：优先取 DDL 的字段和类型；没有 DDL 时只列脚本里
     实际用过的字段（SELECT/GROUP BY/JOIN/WHERE 出现过），
     类型写「待确认（脚本未声明）」，含义只许抄注释或别名原文，
     没有注释写「待人工确认」。
   - 粒度：只能从产出脚本的 GROUP BY/去重键推断，写成
     「推断：一行 = ...（依据：<脚本> 的 group by ...），待人工确认」。
   - DDL 来源：有 DDL 写文件路径；没有写「无本地 DDL，由脚本反推」。
   - 负责人、状态（推荐/谨慎/已下线）、坑：脚本里没有，
     一律「待人工确认」；不许用文件新旧推测表已下线。
4. 输出：一表一文件 docs/table-cards/<表名>.md；同名旧卡已存在时
   先给我看差异摘要，不要直接覆盖。
5. 分批执行：一批最多处理 <10> 张表，批与批之间停下来等我确认。
6. 每批最后给一张汇总表：表名 | 卡已生成 | 待人工确认项数量，
   并把所有「待人工确认」按表汇总成一份人工待办清单贴出来，
   我只补这份清单里的问题。
```
