# 试点验收清单：Skill 算不算「能用」按这个测

> 当前状态（2026-11-09）：Skill v0.5 是「试点可用」——流程、红线、
> 环境约束都对齐了真实场景，配套工具在合成样例上测过；但还没在
> 内部 CLI + 真实任务上跑过一遍。跑完下面 4 个测试都过，
> 才升 v1.0 算正式可用。测试都在公司本地做，记录只记现象不记真实数据。

## T1 加载测试（5 分钟，先做这个）

- [ ] 把 `SKILL.md` 放进内部 CLI 的 skills 目录（或它规定的位置），
      新开会话，点名让它用 sparksql-dev 处理一个简单需求。
- 通过标准：CLI 能识别并加载 Skill，回复里体现了强制流程
  （先问口径、先给方案），而不是直接甩一整段 SQL。
- 不过怎么办：把 CLI 的报错原文、或它自带示例 Skill 的目录结构/文件头
  发回维护者，八成是格式（frontmatter 等）要适配，改格式不动内容。

## T2 测试脚本任务（低风险真活）

- [ ] 选一个单次数据分析类的真实小需求，让它按流程出方案 → 生成 .sql →
      跑离线静态校验。
- 通过标准：关键字小写、前逗号；分区过滤带 `pt_d`（涉及的层级齐全）；
  变量只有 `set` + `${...}`；字段没有编的（对照你熟悉的表核对）；
  交付时声明了「未实际运行」。
- 记录：它问了哪些本该查卡片的问题、哪一步想跳步。

## T3 正式脚本任务

- [ ] 选一个要落表的正式脚本需求（或改一个老脚本）。
- 通过标准：T2 全部 + 注释头按本地还原后的模板齐全、改老脚本时
  `@Modify` 已更新；UDF 只用了清单里有的（清单还没填的，
  它应该明说未找到而不是自创——出现自创就是不过）。
- 前置：本地先把 `{{SCRIPT_HEADER_FULL}}` 还原成真实注释头模板，
  这条不过先分清是模板没给还是它没执行。

## T4 日志闭环

- [ ] 任一测试任务提交运行后（成功失败都行），把 SparkUI 日志存成文件
      放进项目目录，让它读文件分析。
- 通过标准：能摘出关键报错/Stage 并定位到 SQL 具体位置；
  失败时给改好的完整文件，而不是只给口头建议。

## 验收记录格式（每条一行，贴回给维护者即可，不要贴真实日志/表名）

```text
T几 | 过/不过 | 现象一句话 | 卡在哪一步（加载/流程/分区/字段/UDF/排版/日志）
```

四条全过 → 冻结 v1.0；某条不过 → 按记录改 Skill 对应小节，
升一个小版本重测那一条，不推倒重来。
